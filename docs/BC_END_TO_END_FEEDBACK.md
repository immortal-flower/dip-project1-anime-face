## 3. 可以确认的结论

1. B 和 C 的代码接口已经接通：检测框可以传给 28 点回归器，并产生原图坐标关键点。
2. C 模型在人工真值框下能够覆盖 38/38 张，说明关键点回归器不是当前端到端覆盖率的首要瓶颈。
3. 使用 B 框后只有 3/38 张满足 IoU≥0.5；无论原因来自候选召回、分数过滤、NMS、跨域泛化或框语义差异，检测端都是当前完整系统首先要诊断的环节。
4. 端到端成功率 2/38=5.26%，不能把当前完整系统描述为可用精度。

## 4. 必须保留的可比性限制

`data/processed/joint_a_c_v1/landmarks_validated.json` 中 C 的 AnimeFace 样本是已经裁好的头像图，bbox 为整张图 `[0,0,width,height]`。B 在 Manga109 上学习和输出的是复杂页面中的局部人脸框。

因此，AnimeFace 上的 IoU≥0.5 同时测量了以下因素：

- B 检测器能否跨数据域找到人脸；
- B 的局部脸框能否与 C 的整图头像框达到相同尺度和边界定义；
- 分数阈值和 NMS 是否删除了可匹配候选；
- 框偏移是否破坏 C 回归器的归一化坐标假设。

这 38 张结果是有价值的端到端兼容性压力测试，但不能与 Manga109 整页检测 Recall 直接等价，也不能只根据它断言所有 35 个 FN 都是“没有看到人脸”。其中一部分可能是检测到了局部脸区域，但与整图范围真值框的 IoU 不足 0.5。

## 5. 后续诊断顺序

现有 Manga109 108 页 test 和 AnimeFace 38 张 test 都已经暴露，不能继续用于阈值、框扩张比例或模型容量选择。改进只能先在固定 train/validation 上完成。

### 5.1 先取得 C 的可复核产物

C 应交付：

- 38 张逐图真值框、预测框、score、最大 IoU 和匹配结果；
- oracle 与 detected 两套逐图 NME、visibility、归一化距离和失败原因；
- 检测器、关键点模型、数据清单和评价脚本的 SHA256；
- 完整运行命令及缺失图片列表。

### 5.2 在 AnimeFace validation 上拆解 FN

使用现有 25 张 validation，不读取 38 张 test 来选择参数，分别统计：

1. 分数过滤前所有滑窗候选的最大 IoU；
2. top-K 截断后的最大 IoU；
3. NMS 后的最大 IoU；
4. 最终 `score_threshold` 后的最大 IoU；
5. 在 IoU=0.3/0.4/0.5 下的 proposal recall。

若过滤前已有高 IoU 候选，问题主要在阈值、NMS或排序；若候选中心正确但框普遍偏小，问题主要在框目标定义和尺度校准；若过滤前也没有候选，则需要改进特征、训练域或扫描尺度。

### 5.3 只在 validation 选择改进

- 用 C train/validation 的正例和域匹配负例补充检测训练，不使用 C test。
- 将阈值选择目标从最大 F1 改为显式的最低召回约束或 F2，并同时报告误报代价。
- 若验证集证明只是尺度定义不一致，可注册固定的框扩张/中心校准规则，再冻结参数。
- 分开报告“局部人脸框任务”和“整图头像框任务”；不要用自动把整张裁剪图当作检测结果的捷径冒充整页检测能力。
- 若需要新的无偏最终结论，应新增未参与调参的端到端 holdout，或在 Manga109/其他整页图上补充与人脸框对应的 28 点标注。

## 6. 当前对外结论

B 已完成传统 Cascade 检测链路，C 已完成正确人脸框条件下的 28 点回归评价，两者接口也已运行。但冻结 B 检测器在 Manga109 上召回很低，在 C 的跨域整图框协议下端到端覆盖率同样很低。下一阶段应先在 validation 上区分“候选没产生、候选被过滤、框尺度不一致”三类原因，再决定重训、阈值目标或框校准方案。
